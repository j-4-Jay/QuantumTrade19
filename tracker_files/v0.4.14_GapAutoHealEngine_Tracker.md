## 1. User Questions Answered

- "Is a dedicated engine already present?" NO. Gap healing previously lived
  inside the Reflex UI state layer (state/app_state_mixins/deep_history_card_mixin.py),
  triggered once from on_load. This was architecturally wrong.
- "Why isn't it doing its job?" Because it only ran ONCE, at app startup,
  from the UI layer. Any gap appearing after that first pass (or on a
  session where Settings was never opened) was never healed again.
- "Data should never be deleted until manual delete" - CONFIRMED already
  true. The only deletion path in the entire codebase is the Delete button
  (delete_symbol_history -> MarketDataMonitor.delete_deep_history). Nothing
  else - not the poll loop, not the old startup scan, not this new engine -
  ever deletes candle rows.
- "Download duration of one symbol should not affect another" - CONFIRMED
  already true structurally. DeepHistoryDownloaderWorker keys every active
  download and status dict entry by (symbol, timeframe), so one symbol's
  Download Duration action can never pause, cancel, or interfere with any
  other symbol's download.

## 2. What Changed

### New file
```
D:\QuantumTrade19\engines\workers\market_data\gap_auto_heal_worker.py
```
`GapAutoHealWorker` - a real background thread, owned by MarketDataMonitor,
that runs for the entire lifetime of the app process (independent of any
browser session). Every 60 seconds it scans every active symbol x every
configured TF (1m/5m/15m) for an existing internal gap (2+ physical SQLite
ranges) and, only if that TF is not already downloading, triggers ONE
bounded heal download covering just that TF's own existing earliest-to-
latest span - never expanding beyond what a human already downloaded.
`heal_now(symbol, timeframe)` is exposed for both the automatic scan and a
manual retry, so there is one implementation, not two divergent copies.

### Replaced files
```
D:\QuantumTrade19\engines\monitors\market_data_monitor.py
D:\QuantumTrade19\state\app_state_mixins\deep_history_card_mixin.py
D:\QuantumTrade19\ui\components\deep_historical_data_card.py
```

- `market_data_monitor.py`: constructs `GapAutoHealWorker`, starts it in
  `MarketDataMonitor.start()`, stops it in `stop()`. Adds
  `heal_gap_now(symbol, timeframe)` as the public entry point for a manual
  retry, delegating to the same worker.
- `deep_history_card_mixin.py`: `heal_tf_gap()` now just calls
  `engine.market_data.heal_gap_now(...)` instead of containing its own
  bounded-heal logic. `startup_scan_deep_history_background()` now only
  fires broker ceiling probes - gap healing is handled continuously by the
  new backend engine, not a one-time UI event. Added `present_range_label`
  (actual earliest-to-latest calendar dates physically stored) and
  `gap_labels` (each individual gap's actual start/end dates and duration)
  to `TfCoverageRow`, and folded them into a richer tooltip.
- `deep_historical_data_card.py`: mini bars now show the actual present-data
  date range and a gap count directly under each bar (not hidden inside the
  tooltip only), so the real local DB status is visible at a glance.

## 3. Data Integrity / Independence Preserved

- The new engine only ever reads SQLite via `CandleStoreWorker.get_physical_ranges`
  and starts downloads via the existing, unchanged `DeepHistoryDownloaderWorker`
  - no new write path, no manifest interaction, no broker-probe
  contamination of local coverage (all v0.4.8 locked rules intact).
- The engine's bounded heal is identical in shape to the old (now-removed)
  mixin-level implementation: it never requests data beyond a TF's own
  existing earliest-to-latest span.
- Confirmed no automatic deletion path exists anywhere in the touched files.
- Confirmed per-symbol independence is structural (via `(symbol, timeframe)`
  keys in `DeepHistoryDownloaderWorker`), not something this patch needed to
  add - only verified and documented.

4. Confirm no traceback.
5. Watch `logs\quantumtrade19.log` for a `gap_auto_heal_started` line

6. Open Settings -> Data & Connection. Confirm each mini bar now shows an

   appears under that bar, and hovering shows the exact gap start/end

8. Leave the app running (Settings tab can be closed) for several minutes
   with a known gap present - confirm the gap eventually closes on its own
   without any user interaction, verified either by the bar going fully
   green or by a fresh SQLite row-count check.
9. Start a Download on one symbol; confirm a completely different symbol's
   existing download/progress is unaffected (percentages advance
   independently, no cross-symbol pausing).
10. Confirm Delete still only removes data for the symbol/TF explicitly
    clicked, and confirm no gap ever "disappears" due to accidental
    deletion by the new engine (it only ever downloads, never deletes).
