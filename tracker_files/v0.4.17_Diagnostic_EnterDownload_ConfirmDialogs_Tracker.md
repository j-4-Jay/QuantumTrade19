## 2. What Was Built This Round

### NEW: standalone diagnostic script
```
D:\QuantumTrade19\Diagnose_DeepHistory_v1.py
```
Read-only. Does NOT import any app engine code - talks directly to SQLite
and to the broker's raw HTTP endpoint, so it works even if the running app
itself is misbehaving. Reports, in order:
1. Physical SQLite row counts, span, and % missing (gap) per symbol/TF -
   ground truth, independent of any UI display bug.
2. Manifest file contents per symbol/TF, for cross-checking against SQLite.
3. A raw HTTPS request to the exact broker candles endpoint the app itself
   calls - this directly tests whether "broker ceiling never fetched" is a
   NETWORK/FIREWALL/SSL problem on this machine (which would also explain
   "gap filling not working", since both features depend on the exact same
   outbound HTTPS call succeeding).
4. Recent log lines containing gap_auto_heal_started / triggered /
   scan_failed / probe_failed / download activity - reveals whether the
   backend engine thread is even running, or silently erroring.
5. The tail of errors.log.
6. A static source-code check confirming whether the CURRENTLY INSTALLED
   market_data_monitor.py actually contains the v0.4.14/v0.4.15
   GapAutoHealWorker wiring - if a previous file replacement was missed or
   reverted, this will show FAIL and explain everything at once.

### Enter-to-download + smart confirmation
`state/app_state_mixins/deep_history_card_mixin.py` /
`ui/components/deep_historical_data_card.py`:
- Removed the Download button entirely.
- `handle_duration_keydown(symbol, key)` triggers `request_download(symbol)`
  on Enter.
- `request_download` compares the requested day count against the largest
  already-present local coverage across the symbol's three timeframes. If
  smaller, it opens a plain-language confirm dialog stating the exact
  already-present duration and offers "Proceed Anyway" (safe - no data is
  ever deleted or reduced by this) or "Cancel". If the requested value is
  already large enough, the download starts immediately with zero
  interruption.

### Delete confirmation
`_delete_confirm_button` wraps Delete in a real `rx.alert_dialog` requiring
an explicit "Delete Permanently" click before `delete_symbol_history` runs.
Previously it was a single, unconfirmed click - if that seemed like "it's
not working", this is why: it *was* deleting, just without any visible
confirmation step, so a single accidental click could look like nothing
happened when it may have actually deleted data.

### Per-symbol independence (re-verified, not re-built)
- `request_download`, `_start_download_now`, `cancel_symbol_downloads`, and
  `delete_symbol_history` all loop ONLY over the one `symbol` parameter
  passed in.
- `engine.market_data.start_deep_history` / `cancel_deep_history` /
  `delete_deep_history` all key their internal state by
  `(symbol, timeframe)` in `DeepHistoryDownloaderWorker` - unchanged and
  re-confirmed structurally independent per symbol.

## 3. NOT Yet Fixed (Pending Diagnostic Evidence)

- ETA stuck in permanent "Estimating..." animation.
- Broker ceiling never fetched at all.
- Gap filling not working.

These three are very likely ONE root cause, not three separate bugs: if
outbound HTTPS calls to the broker are failing/hanging/blocked on this
machine or network, ALL THREE would present exactly this way
simultaneously - the downloader would never receive real candle data (no
progress ever advances -> ETA never resolves past "Estimating..."), the
depth prober would never receive real ceiling data (stays "Not probed
yet"), and gaps would never close (no new candles ever arrive to fill
them). `Diagnose_DeepHistory_v1.py` section 3 tests this directly.

It is also possible the previously-provided v0.4.14/v0.4.15 files were not
actually installed/kept - section 6 of the diagnostic checks this exactly.
