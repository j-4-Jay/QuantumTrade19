## 2. Root Cause Found

`engines/workers/market_data/candle_store_worker.py`'s
`get_local_coverage()` and `get_missing_ranges()` previously:
- Built a Python `set()` of EVERY individual expected timestamp in the
  requested range (for a 555-day, 1-minute request: ~800,000 integers).
- Re-fetched EVERY stored row via `get_all_timestamps()` on every single
  call.
- Were both called multiple times per download-loop iteration (once at
  the top of each loop pass via `_emit_progress`, again after every
  persisted batch).

For a symbol/TF with hundreds of thousands of rows and many separate small
gaps (as B-BTC_USDT 1m apparently has, likely from earlier interrupted
test downloads during this thread's iterative debugging), this became
severely expensive Python-level work, repeated constantly. Because this
work is CPU-bound pure-Python (building/comparing giant sets), it also
holds the GIL for extended stretches, which is the most likely unifying
explanation for why broker-ceiling probing and other background activity
also felt unreliable/stuck at the same time - not three separate bugs, but
one shared bottleneck starving everything else running in the same
process.

## 3. Fix Applied

`engines/workers/market_data/candle_store_worker.py` rewritten:

- `get_physical_ranges()`: now computes contiguous stored ranges entirely
  in SQL using the standard "gaps and islands" window-function technique
  (`ROW_NUMBER() OVER (ORDER BY open_time)`). SQLite computes this using
  its own index in milliseconds, regardless of table size - zero
  Python-side materialization of individual timestamps.
- `get_missing_ranges()`: no longer builds a set of every expected
  timestamp at all. Gaps are now derived purely from the (now SQL-fast)
  physical range boundaries clipped to the requested window - O(number of
  gaps), never O(range width / step).
- `get_local_coverage()`: present/required/missing candle counts are now a
  single SQL `COUNT(*)` query plus simple arithmetic - no Python set of
  the entire requested range is ever built just to measure its size.
- Every method's return shape and semantics are IDENTICAL to before - this
  is a pure performance fix, not a behavior change for any caller
  (MarketDataMonitor, DeepHistoryDownloaderWorker, GapAutoHealWorker, and
  the Deep Historical Data card mixin all continue to work exactly as
  designed, just fast now).
