## 1. Diagnostic Evidence (Diagnose_DeepHistory_v3.py)

Direct broker HTTP tests targeting the EXACT gap window B-BTC_USDT 1m was
stuck on (identified by v2's SQL gap-island query):

- Requesting the full ~327-day gap window, limit=1000: broker returned
  exactly 1 row - the candle sitting AT endTime (2026-06-09 20:25 UTC).
- Same window, limit=5: still exactly 1 row, same candle.
- A narrow 1-day slice at the START of the gap (2025-07-17): 0 rows -
  clean empty array.
- A narrow 1-day slice at the END of the gap (right before the boundary):
  still exactly 1 row, same candle.

Conclusion: the broker's public candles endpoint has NO 1-minute candle
history for B-BTC_USDT across most of this window. The single row
returned every time is the SAME already-locally-stored boundary candle,
never anything older - a genuine, real broker-side retention limit, not a
QT19 bug.

## 2. The Actual Bug (in our code)

`DeepHistoryDownloaderWorker` correctly treated a clean EMPTY broker
response as "nothing more here" and stopped. It had NO detection for "the
broker returned data, but the frontier made zero backward progress" - the
exact case proven above. Without that check, the outer download loop kept
re-selecting the SAME unreachable gap every pass, re-fetching and
re-persisting (a harmless but wasteful UPSERT no-op) the identical
boundary candle, forever - explaining the observed "1 row persisted every
~3.5 seconds, indefinitely" symptom precisely.

## 3. Fix Applied

`engines/workers/market_data/deep_history_downloader_worker.py`:

- Extracted gap-filling into `_fill_one_gap()`, which now tracks whether a
  single attempt made ANY real backward progress
  (`batch_oldest < attempt_started_at`).
- If a batch is returned but the frontier did not move backward at all,
  this is now treated EXACTLY like an empty response:
  `broker_ceiling_reached=True` is set and the gap-fill attempt stops.
- The outer `_download_loop` now checks `made_progress` after each gap
  attempt. If it is `False`, the download session ends cleanly
  (`state="broker_ceiling"` or `"incomplete"` as appropriate) instead of
  re-selecting the same unreachable gap forever.
- `GapAutoHealWorker`'s normal ~60s periodic re-attempt is UNCHANGED and
  will still retry this gap later (in case the broker's own retention
  changes) - but each retry now costs one quick, clean request instead of
  an unbounded internal loop.
