## 1. Evidence (real running-app error log, not a standalone test)

Multiple `history_depth_probe_failed` entries across different
symbol/timeframe combinations (B-BTC_USDT 5m, B-ETH_USDT 1m, B-BTC_USDT
1m, B-ETH_USDT 15m), each tracing to the SAME root cause:

```
urllib3.exceptions.ReadTimeoutError: ... Read timed out. (read timeout=10)
```
and
```
TimeoutError: _ssl.c:993: The handshake operation timed out
```

Both occur at the prober's old `timeout=10` boundary. Meanwhile, a manual
standalone diagnostic test using `timeout=15` against the exact same
broker endpoint succeeded every single time (Diagnose_DeepHistory_v1.py,
section 3). This proves the broker itself is reachable and responsive -
the probe's own 10-second timeout is simply too tight when running inside
the full app, where it competes for the network with the WS feed, REST
fallback pollers, and deep-history download threads all at once. A
standalone script has no such contention.

## 2. Fix Applied

`engines/workers/market_data/history_depth_prober_worker.py`:

- `PROBE_TIMEOUT_S` increased from 10 to 20 seconds.
- Added `_request_with_retries()`: retries a failed probe request up to
  `PROBE_MAX_RETRIES = 2` additional times, with a `2.0s` backoff between
  attempts, before giving up and recording an error. A single slow moment
  under real load no longer permanently fails that probe cycle.
- Broker-only isolation is completely unchanged: this worker still never
  touches SQLite or the manifest (locked v0.4.8 rule).
