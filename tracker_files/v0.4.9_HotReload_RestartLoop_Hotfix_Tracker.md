## 1. Problem Found After v0.4.8 Install

After installing the 6 v0.4.8 data-integrity files, the user reported:
- The 1m chart rendered only 4-5 candles no matter how many days were requested.
- The application appeared to "repeatedly restart".

## 2. Diagnostic Evidence

`python -m py_compile` on all 6 replaced files passed cleanly (only cosmetic
`SyntaxWarning: invalid escape sequence '\Q'` from docstring `TARGET PATH:`
lines - harmless).

A full read of `logs\quantumtrade19.log` showed:

```
21:56:48  logging_configured
21:57:00  logging_configured   (12s later)
21:57:04  market_data_monitor_start
21:58:01  logging_configured   (57s later)
21:58:04  market_data_monitor_start
21:59:02  logging_configured   (58s later)
21:59:07  market_data_monitor_start
22:00:01  logging_configured   (54s later)
22:00:05  market_data_monitor_start
```

No Python traceback accompanies any of these restarts in `errors.log`. This
is the signature of a **dev-mode hot-reload loop**, not a code exception.

Confirmed NOT caused by:
- OneDrive/Dropbox/Google Drive sync (user confirmed project folder is not
  cloud-synced).
- A constructor mismatch between the 6 replaced files (verified: `MarketDataMonitor.__init__`
  calls `DeepHistoryDownloaderWorker(manifest=..., on_chunk=..., get_missing_ranges=...,
  get_coverage=...)` and `HistoryDepthProberWorker()` with no args - both match the
  new v0.4.8 constructors exactly).

## 3. Confirmed Root Cause

Reflex's dev-mode hot reloader watches the entire project directory for file
changes by default. The v0.4.8 SQLite-truth architecture writes very
frequently to files that live inside that same watched project tree:

- `data\historical\candles.db` (every candle close + every deep-history batch)
- `data\historical\manifests\*.json` (every `mark_covered()` call)
- `logs\quantumtrade19.log` / `logs\errors.log` (every log line)

Each of those writes was being seen by Reflex's watcher as "a file changed",
triggering a full backend restart roughly once a minute - matching the
observed cadence exactly. This wiped `CandleBuilderWorker`'s live in-memory
1m series and killed in-progress 1m deep-history download threads before
they could finish a single 1,000-candle batch, producing the "only 4-5
1m candles" symptom.

## 4. Fix Applied

`rxconfig.py` now sets `REFLEX_HOT_RELOAD_EXCLUDE_PATHS` (the officially
documented Reflex environment variable for this exact situation) BEFORE
importing reflex, excluding:

- `data\` (candles.db, manifests)
- `logs\` (quantumtrade19.log, errors.log)
- `.web\` (Reflex's own generated frontend build output)
- `tracker_files\` (bundle/tracker markdown files)

Source `.py` files under `engines\`, `state\`, `ui\`, and `config\` remain
fully watched, so normal code-change hot reload still works as expected.

1. Stop QT19 completely (close terminal / stop `reflex run`).
2. Replace `rxconfig.py` with the hotfixed version.
3. Delete the `.web` folder's build cache to force a clean rebuild:
   ```
   Remove-Item -Recurse -Force D:\QuantumTrade19\.web
   ```
4. Start the app:
   ```
   cd D:\QuantumTrade19
   reflex run
   ```
5. Watch `logs\quantumtrade19.log` for at least 5 full minutes.
   - PASS: `market_data_monitor_created` / `market_data_monitor_start`
     appear only ONCE per real app start - not every ~60 seconds.
6. Open Trading Panel, select 1m, and set Display Last Days to a value
   larger than current local 1m coverage.
   - PASS: the combined progress bar stays active continuously without
     resetting to 0% every minute.
   - PASS: 1m candle count in the chart grows over time instead of staying
     stuck at 4-5 candles.
7. Confirm `Available in QT19 Database` for 1m increases as batches persist,
   matching a direct SQLite row count check.
8. Leave the chart open 15+ minutes; confirm no further unexpected restarts
   appear in the log.
